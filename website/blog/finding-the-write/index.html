You edit a paragraph, press Save, and get a reassuring message. A moment later, you reload. The old paragraph is back.

Somewhere in the codebase, something disagrees with what you just saw.

An unfamiliar project gives you plenty of places to look. There’s an editor, a save handler, an autosave queue, a service, and a database layer. Searching for “save” finds several functions. Each looks reasonable on its own.

The useful question is where your text went, and what happened to it afterward.

In our first post, we looked at the research behind Know Your Code. This time, we’re following one symptom through code and checking a fix.

About the example

The example is constructed, so you can reproduce it without someone else’s project or data. The editor, queue, and API boundary are modeled in Python. The storage is a real SQLite database. There’s no browser or network timing to guess at: we control the order of the saves.

01Follow the text

Start with a question you recognize:

“My saved text comes back as an older draft. Follow the save path and show me how that could happen. Don’t change anything yet.”

That gives the investigation a destination. We need to explain the disappearing text.

The editor has two ways to save. Pressing Save sends the current text immediately. Autosave takes a snapshot and puts it in a queue.

Both eventually reach the same document service and database write.

The important detail is what goes into the queue. It holds a copy of the text from the moment autosave was scheduled. Editing the paragraph afterward doesn’t update that copy.

02The later write carries older text

Autosave has already queued “Earlier draft” at revision zero. You keep editing and press Save. Your current paragraph reaches storage first—then that older snapshot gets its turn.

Try that order yourself. The browser simulation below follows the same rules as the Python model. You control the text and the order; there is no network or backend.

That changes where we should work. Reloading faithfully reads the value currently stored. The database accepted both writes. The missing rule is how to decide whether a request still has permission to replace the document.

03Use the revision already on the path

To get there, we followed the same pieces of information through each layer: the document’s ID, its text, and its revision.

A revision is a number that changes whenever the document is saved. The editor loads revision zero. A successful save moves the stored document to revision one.

Our queued autosave still carries revision zero. So does the manual save that was prepared before either request completed.

The original database update receives that number but doesn’t use it. Its rule is simply: find this document and replace its text.

Before · Match the document
UPDATE documents
SET body = ?, revision = revision + 1
WHERE id = ?

The revision gets incremented, but nothing checks whether the incoming request is based on the current version.

The correction adds that condition:

After · Match the document and its revision
UPDATE documents
SET body = ?, revision = revision + 1
WHERE id = ? AND revision = ?

In plain words:

“Replace this document only if it is still the version you edited.”

The comparison and the write happen in the same database statement. If the revision has changed, no row is updated. The service reports a conflict, and the API model returns status 409.

Now we repeat the original sequence.

The manual save arrives with revision zero. It succeeds and moves the document to revision one. The delayed autosave also arrives with revision zero. Its condition no longer matches, so it cannot replace the finished paragraph.

04A conflict still needs a decision

It also creates a responsibility for the editor. A rejected save must leave the user’s draft available. Otherwise, preventing one kind of loss could introduce another.

So the example keeps the text in the editor and explains what happened:

“The document changed. Your draft is still here; compare it before saving again.”

There’s a limit to what the revision check can decide. It knows whether the document has changed. It doesn’t know which paragraph the user prefers.

That distinction becomes clear when we reverse the request order.

Suppose the autosave runs first. It stores “Earlier draft” and advances the revision. The manual save then arrives with the old revision and gets a conflict.

Let autosave arrive first in the experiment ↑

The finished paragraph remains in the editor, but it hasn’t been stored. The user needs to review the current document and choose how to proceed.

Automatically retrying every rejected write would let stale text overwrite newer work again. A complete editor needs a deliberate policy for conflicts: compare versions, merge suitable changes, or let the user choose a replacement. This example makes that choice visible and checks that a save after review can succeed.

We also tried two editors loading the same document revision. The first saves successfully. The second gets a conflict and retains its own draft.

05Check more than the happy path

Across the checks, we established four things:

  • ✓
    The original sequence reproduces the overwrite.
  • ✓
    The revision check blocks a delayed stale save.
  • ✓
    Reversing the order produces a visible conflict while preserving local text.
  • ✓
    Two editors cannot silently replace each other’s changes from the same starting revision.

Reopening the database confirms that the accepted result is stored beyond the original connection.

Those checks give us a useful boundary around the conclusion. We’ve verified the state transitions in this example. The browser experiment illustrates those rules with controlled timing and an in-memory store. A production editor would still need checks for its actual queue, network requests, and conflict interface.

06One question makes the code less unfamiliar

This is the kind of understanding we want Know Your Code to help build.

An unfamiliar codebase becomes easier to navigate when you carry one concrete question through it. Here, the question led us from the editor to the queue, from the queue to the database, and from an apparently successful save to a missing revision condition.

Following the text mattered more than reading every file. Following the second writer mattered more than stopping at the first successful request. Trying the opposite order exposed what the fix still needed from the user.

You can ask the same questions in your own project:

  • “What value does this action send?”
  • “What else can write to the same place?”
  • “What happens if those writes arrive in the opposite order?”

Start with one behavior you can recognize. Ask for the path, the competing writers, and a check you can run. By the end, “my text disappeared” should become a specific sequence you can explain—and a result you can verify.
